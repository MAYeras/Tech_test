# Разбор документов: LLM (Groq) + Python-аудит

Сервис принимает текст документа (счёт, КП, акт) и возвращает JSON по фиксированной схеме.
Архитектура в два шага:

```
текст ─► LLM (Groq, openai/gpt-oss-120b, json_schema, temperature=0)
          │
          ├─ невалидный JSON / ошибка схемы ──► ретрай с текстом ошибки (до 3 попыток)
          │                                     └─ не исправилась ──► пустой результат + VALIDATION_FAILED
          ├─ ошибка API (нет ключа, сеть, лимит) ──► пустой результат + BACKEND_ERROR (без ретраев)
          ▼
   Python-аудит (audit_and_enrich):
     проверка каждого значения по тексту → поиск противоречий → арифметика → field_confidence → warnings
```


## Запуск

```bash
pip install -r requirements.txt
export GROQ_API_KEY="..."                      # ключ только из окружения, в коде его нет

python real.py                                  # встроенный пример
python real.py data/docs/07_HARD_conflicts.txt  # свой файл
python eval_real.py -v | tee groq_eval.txt      # весь набор на Groq + отчёт
python -m pytest -q test_real.py                # 11 тестов логики (Groq не вызывают)
```

Код выхода `real.py`: `0` — ответ прошёл валидацию, `2` — нет (в stdout всё равно безопасный JSON со всеми `null`).

## Схема

`doc_type` (invoice | commercial_offer | act | unknown), `supplier_name`, `supplier_bin`, `doc_number`, `doc_date` (YYYY-MM-DD),
`currency` (KZT | USD | EUR), `total_amount`, `vat_amount`, `line_items[{name, qty, price}]`, `field_confidence`, `warnings`.
Схема проверяется pydantic: лишние ключи запрещены, `doc_date` обязана быть настоящей датой в формате YYYY-MM-DD,
иначе ответ уходит на ретрай.

## Правила

**Чего нет в документе — `null`.** Аудит проверяет по тексту документа каждое значение:
* БИН — ровно 12 цифр, стоит в тексте после метки БИН/БСН/BIN и принадлежит поставщику, а не заказчику/покупателю;
* дата — есть в тексте и это не срок («действительно до», «оплатить до»);
* итог и НДС — это число написано в документе (НДС не считается по ставке, итог не суммируется по позициям);
* название, номер, валюта, тип документа и каждая позиция — подтверждаются текстом.

**Противоречия — в `warnings`.** `CONFLICT_DATE`, `CONFLICT_TOTAL` ищет код независимо от модели. Правило выбора значения:
1. **Дата документа** — первая по тексту «первичная» дата (после «от», «Дата», «Составлено», «Выставлен», «күні»). Если первичных дат несколько и они разные — берётся первая, остальные попадают в `CONFLICT_DATE`.
2. **`total_amount` — итого к оплате с НДС.** Метка «к оплате»/«итого с НДС» важнее «итого»; при равном приоритете — первая по тексту.
3. «Итого 160 500 + НДС 25 680 = к оплате 186 180» — не противоречие. Две разные суммы, которые НДС не объясняет, — `CONFLICT_TOTAL`.
4. Если аудит нашёл конфликт, а модель выбрала иное значение, оно заменяется по правилу.

**Прочее.** `vat_amount = null` при «НДС не облагается» (+ `VAT_EXEMPT`). Двуязычное название — русская форма. Если в числах были OCR-ошибки (`O→0`, `l/I→1`), аудит сверяет значения с исправленным текстом, добавляет `OCR_FIXED` и ограничивает доверие числовых полей уровнем 0.7. Итог сверяется с позициями: подходит и «итого = позиции», и «итого = позиции + НДС»; если у какой-то позиции нет `qty` или `price`, арифметика не проверяется.

## Что происходит, если ответ не прошёл валидацию

* Невалидный JSON, неверный тип поля, неверный формат даты, лишний ключ → модели возвращается текст ошибки, ещё до 2 попыток.
* Не исправилась за 3 попытки → `doc_type: "unknown"`, все поля `null`, `warnings: ["VALIDATION_FAILED: …"]`, код выхода 2.
* Ошибка API (нет ключа, сеть, лимит) → `BACKEND_ERROR`, без ретраев. В отчёте eval такие документы выделяются красной шапкой «отчёт недействителен», чтобы их не принять за ошибки модели.

Эти ветки проверяют тесты `test_real.py`, подставляя заранее заданные ответы вместо вызова Groq. На реальной модели в прогоне ниже ретраи не потребовались.

## Тестовый набор

`data/docs/*.txt` + `data/gold/*.json`: 3 документа заказчика и 8 моих; из них 3 сложных (противоречия, ошибки OCR, сумма прописью с отсутствующими полями и смесью каз./рус.).

| # | Документ | Что проверяет |
|---|---|---|
| 01 | Счёт «Алматы Трейд Компани» (заказчик) | таблица, итог + НДС = к оплате |
| 02 | КП «Digital Solutions» (заказчик) | почти всё `null`; две даты, одна из них — срок; итога нет |
| 03 | Шот-фактура, каз.+рус. (заказчик) | OCR в БИН, дата «09 қазан 2026», сумма прописью по-казахски, «НДС не облагается» |
| 04 | Счёт в USD | десятичная запятая, НДС нет (не считать), БИН покупателя рядом |
| 05 | Акт в EUR | «в т.ч. НДС», БИН заказчика |
| 06 | КП с НДС в ₸ | «Итого с НДС», срок действия ≠ дата документа |
| 07 | **HARD** противоречия | две даты документа, два разных итога |
| 08 | **HARD** OCR | `l5.O3.2O26`, `23O54OOl3I9O`, `48 OOO`, `Ne 88` |
| 09 | **HARD** прописью, пропуски, каз.+рус. | БИН только у заказчика, даты нет, итог словами |
| 10 | Товарная накладная | тип не из enum → `unknown`, поля извлекаются |
| 11 | Письмо без данных | ИИН физлица, «бюджет около 2 000 000 тенге», дата встречи; всё должно быть `null` |

Решения по эталону: тип документа 3 — `invoice` (по заголовку «Шот-фактура»); `vat_amount = null` при «НДС не облагается»; в документе 11 `currency = KZT` (в тексте есть слово «тенге»); у позиции «1 ед. — 340 000» `price = 340000`.

### Разбор семи расхождений

| Документ, поле | Что вернула модель | Причина | Что сделано после прогона |
|---|---|---|---|
| 01, 03, 06 · `supplier_name` | `Алматы Трейд Компани` вместо `ТОО "Алматы Трейд Компани"` | модель не включает организационно-правовую форму; в промпте это не было сказано | в промпт добавлено правило 11: название вместе с ТОО/АО/ИП как в документе |
| 08 · `doc_number` | `Ne 88` | модель оставила слово-метку; аудит его пропустил, так как «ne 88» есть в тексте | код срезает «№», «No», «Ne» перед номером + правило 12 в промпте |
| 03 · `line_items` | название `Оказание услуг` | эталон содержал двуязычное название, что противоречит нашему правилу 10 (двуязычное → русская форма); модель его применила | исправлен эталон (название позиции — русская форма). Это правка эталона после прогона, о ней сказано здесь намеренно |
| 11 · `supplier_name` | `ТОО «Альфа Групп»` из подписи письма | **настоящая галлюцинация**: название есть в тексте, поэтому проверка по тексту её не ловит | правило 11 в промпте: организация из подписи письма поставщиком не является |
| 11 · `currency` | `null` | эталон `KZT` (в письме есть слово «тенге»); поведение модели спорное: это бюджет в разговоре, а не валюта документа | не менял: оставлено как пропуск |

**Важно: правки из последнего столбца (кроме эталона) я не перемерял.** Прогон выше сделан до них; результат после них нужно получить повторным `python eval_real.py -v`.

## Ограничения (честно)

* **Аудит в этом прогоне не вмешался ни разу** (`Вмешательства аудита: нет`): модель сама выполнила правила. Поэтому прогон не показывает пользу аудита на реальной модели; его логика проверена только тестами с заранее заданными ответами. Единственную галлюцинацию (документ 11) аудит поймать не мог: проверка «есть ли значение в тексте» не отличает поставщика от отправителя письма.
* **`field_confidence` не различает верное и неверное:** в среднем 0.92 у верных полей и 0.90 у неверных. Это константы по типам проверок, а не калиброванные вероятности; ошибки в этом прогоне были «смысловые» (форма названия), и константы их не видят.
* **Итог, написанный только прописью**, аудит обнулит как «посчитанный моделью», если числа нигде нет цифрами. В документах 3 и 9 число есть в строке позиции, поэтому они проходят.
* Контрольная сумма БИН не проверяется. Позиции проверяются только на наличие названия и чисел в тексте.
* 11 документов и один прогон — это smoke-набор: `temperature=0` не гарантирует одинаковый ответ при повторном запуске.
